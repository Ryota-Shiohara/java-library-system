# 図書館システム共同実装計画

## 1. 方針

この計画は、ryotaとkumpeiの両名が、設計・実装・テスト・レビューに明確な成果を残し、課題の必須要件と加点要素を安定して完成させることを目的とする。

分担は単純な「バックエンド担当／画面担当」にはしない。各自がモデル、業務ロジック、GUI、JUnitテストを担当する縦割りとし、レポートで双方の技術的貢献を説明できるようにする。

## 2. 課題上の重要条件

- 本と会員の情報を追加・削除・修正・閲覧できること。
- 本の貸出・返却ができ、貸出中の本について借用者を確認できること。
- GUIは加点が見込めるため、Java Swingで実装する。
- すべての実装は英語で行う。ソースコード、識別子、コメント、Javadoc、テスト名、UI表示、エラーメッセージ、ログ出力を含め、日本語を使用しない。
- 実行に必要な本体コードはJava SEだけで完結させる。
- `.class`ファイルは提出しない。
- 外部ライブラリを使う場合は、名称、バージョン、入手先、導入方法をレポートに記載する。
- 共同制作者の氏名・学籍番号、分担内容、共同作業で難しかった点をレポートに明記する。

## 3. 推奨アーキテクチャ

```text
src/main/java/library/
├─ Main.java
├─ model/          Book, Member, Loan, LoanHistory, NdcCategory
├─ repository/     ファイル保存・読込
├─ service/        本管理、会員管理、貸出返却の業務ルール
└─ ui/             Swing画面、ダイアログ、テーブルモデル

src/test/java/library/
├─ model/
├─ repository/
└─ service/
```

GUIからファイルを直接操作せず、`UI -> Service -> Repository`の順に呼び出す。これにより、GUIを起動せずに業務ロジックをJUnitで検証できる。

### 英語限定ルール

英語限定の対象は、単に画面表示だけではなく、実装に含まれるすべての文字列と記述である。

- クラス名、メソッド名、変数名、定数名、パッケージ名、ファイル名。
- 行コメント、ブロックコメント、Javadoc、TODO、FIXME。
- JUnitのクラス名、メソッド名、`@DisplayName`、テストデータ内の説明文。
- ボタン、ラベル、テーブル見出し、ダイアログ、バリデーションメッセージ。
- 例外メッセージ、ログ、コンソール出力。
- ソースコードへ埋め込むサンプルデータ。

README、`docs/`内の計画書、提出レポートは実装コードではないため日本語でよい。Pull Requestのレビューでは、マージ前に日本語が実装へ混入していないことを確認する。

## 4. 担当分担

| 領域 | ryota | kumpei |
|---|---|---|
| モデル | `Book`、NDC分類、貸出履歴、在庫数の不変条件 | `Member`、`Loan`、貸出期限 |
| 業務ロジック | 本のCRUD、NDC分類の検索・集計、貸出履歴連携、在庫・検索 | 会員CRUD、貸出・返却、借用者照会 |
| 永続化 | 保存形式、共通ファイルI/O、本・NDC分類・貸出履歴データ | 会員・貸出データの保存読込と整合性確認 |
| GUI | アプリ枠、Books画面、書籍編集ダイアログ、NDC分類・履歴表示 | Members画面、Loans画面、貸出返却ダイアログとの連携 |
| JUnit | 本・在庫・NDC分類・貸出履歴・永続化テスト | 会員・貸出返却・照会テスト |
| レポート | 設計、保存方式、テスト方針 | 操作方法、GUI、追加機能、共同作業記録 |
| レビュー | kumpei担当コードをレビュー | ryota担当コードをレビュー |

作業量の目安は各25時間前後とする。kumpeiは画面数が多く、ryotaは共通基盤と永続化の難易度が高いため、総量はほぼ均衡する。

## 5. 共有インターフェース

初日に以下だけを二人で確定し、以降は担当ブランチで並行作業する。

- IDの形式と重複時の扱い。
- `Book`、`Member`、`Loan`、`LoanHistory`のフィールドと、NDC分類コードの扱い。
- 1会員が同じ本を複数冊借りられるか。
- 貸出期限、延滞判定、削除制約。
- Serviceの公開メソッド名、引数、例外。
- 保存先、文字コード、保存形式。
- GUIの英語表記と画面遷移。
- 返却時にアクティブな貸出を履歴へ移す処理、履歴の保存順序、失敗時の状態。
- NDC分類の表示名、登録・編集画面、検索・集計画面の仕様。

推奨ルールは「貸出中の本・会員は削除不可」「所有冊数を貸出中冊数より少なく変更不可」「同一会員による同一タイトルの重複貸出不可」「貸出期間14日」である。

## 6. 優先順位

### 必須（P0）

- 本・会員のCRUD。
- 貸出・返却。
- 所有冊数、貸出中冊数、利用可能冊数の表示。
- 本から借用者を確認する機能。
- 会員から借りている本を確認する機能。
- データの保存と再起動後の復元。
- 入力検証とエラー表示。
- JUnitテストと、誰でも再実行できる手順。

### 高価値の加点候補（P1）

- Swing GUI。
- タイトル、ジャンル、会員名による検索・絞り込み。
- 貸出期限と延滞表示。
- 貸出可能冊数が0のときの明確な警告。
- 一覧の並べ替え。
- テスト結果をレポートに表で掲載。

### ryota担当の＋α実装（P2・実装予定）

- NDC第1次区分（`0`から`9`）の登録・編集・一覧表示。
- NDC分類による本の検索・絞り込み。
- NDC分類ごとの蔵書数、貸出中冊数、利用可能冊数の集計表示。
- 返却済み貸出の履歴保存、表示、検索・絞り込み、再起動後の復元。
- 貸出履歴とNDC分類を連携した分類別貸出回数の集計。

これらは単なるアイデアではなく、必須機能の完成後にryotaが実装する加点狙いの追加機能とする。すべてGUIから操作・確認できる状態にし、JUnitまたは再現可能な手動確認手順をレポートへ記載する。貸出返却処理と履歴記録の公開API、保存形式、返却失敗時の整合性は、実装前に二人で合意する。

### その他の追加候補（余裕があれば）

- CSVエクスポート。
- ダッシュボードの件数表示。

P0と既存P1が安定するまで、ryota担当のP2実装には着手しない。

## 7. JUnitテスト計画

テストには`junit-platform-console-standalone-6.1.1.jar`を使用する。本体はJava SEのみで動作し、JUnitは`src/test/java`のテストにだけ使用する。JARはGitに含めず、`lib/`へ各自が取得する。

- バージョン: JUnit Platform Console Standalone 6.1.1
- 入手先: https://central.sonatype.com/artifact/org.junit.platform/junit-platform-console-standalone
- 公式手順: https://docs.junit.org/6.1.1/running-tests/console-launcher.html
- ライセンス: Eclipse Public License 2.0

提出レポートには、上記4点、JARの配置先、コンパイル・実行コマンドを記載する。採点者がJUnitを用意しなくても本体だけを`javac`でコンパイル・実行できる状態を維持する。

最低限のテストケースは次のとおり。

| 対象 | 正常系 | 異常系・境界値 |
|---|---|---|
| Book | 登録、修正、検索、削除 | 空タイトル、冊数0以下、ID重複、貸出中削除 |
| Member | 登録、修正、借用一覧、削除 | 空氏名、ID重複、貸出中削除 |
| Loan | 貸出、返却、借用者照会 | 在庫0、不明ID、重複貸出、二重返却 |
| Repository | 保存後の再読込、複数件 | ファイルなし、壊れたデータ、特殊文字 |
| Integration | 登録から貸出・保存・再起動・返却 | 操作失敗後に状態が変わらないこと |
| NDC classification | 登録、表示、検索、分類別集計、再読込 | `0`未満、`9`超過、未定義コード、保存失敗 |
| Loan history | 返却履歴の記録、表示、検索、再起動後の復元 | 二重記録、返却失敗、履歴と貸出中状態の不整合 |

テスト名は英語で「条件と期待結果」が分かるようにする。例: `checkoutFailsWhenNoCopyIsAvailable()`。

## 8. Git運用

- `main`は常にコンパイル可能な状態にする。
- ブランチ名は`feature/ryota-books`、`feature/kumpei-circulation`のように担当者と目的を含める。
- 1コミットは1つの意味のある変更に絞る。
- Pull Requestには実装内容、確認方法、テスト結果を記載する。
- マージ前に必ず相手がレビューし、JUnitが全件成功していることを確認する。
- 同じファイルを同時編集しない。共通ファイルの変更予定は先に共有する。
- コミット履歴を分担証拠として残し、squashで一人分にまとめない。

### Pull Requestを出すタイミング

完成までブランチを抱え込まず、APIや画面の骨格ができた時点でDraft PRを出す。

| 日付・条件 | ryota | kumpei |
|---|---|---|
| 7月14日・公開APIとテスト骨格ができた時点 | Book、BookService、Repository契約のDraft PR | Member、Loan、LoanService契約のDraft PR |
| 7月15日・担当CRUDが動作しテスト成功 | Books CRUD・Books画面のPRをReady for reviewにする | Members CRUD・Members画面のPRをReady for reviewにする |
| 7月16日・貸出返却の主要フロー完成 | kumpeiの貸出PRをレビューし、在庫連携を確認 | 貸出・返却・借用者照会・Loans画面のPR |
| 7月17日・保存と再読込が成功 | 永続化統合PR | 永続化統合PRをレビューし、会員・貸出の復元を確認 |
| 7月18日・加点機能と異常系テスト完成 | 検索・NDC分類・保存境界値・レビュー修正PR | 期限・延滞表示・貸出境界値・レビュー修正PR |
| 7月19日・提出候補版 | 貸出履歴、分類別貸出集計、最終PRをレビューし、mainへマージ | 貸出履歴の返却連携を確認し、最終PRをレビューしてmainへマージ |

Draft PRでは未完成箇所をチェックリストで示す。Ready for reviewへ変更する条件は、本体がコンパイル可能、担当JUnitが全件成功、手動確認方法がPR本文にあることとする。共有APIを変更するPRは、実装を進める前に相手の承認を得る。

### mainへマージするタイミング

マージは日付だけで自動的に行わず、次の条件をすべて満たした時点で行う。

1. PR作成者以外の担当者がレビューし、Approveしている。
2. `src/main/java`がコンパイルできる。
3. 既存テストと追加したJUnitテストがすべて成功する。
4. 実装全体に日本語が含まれていない。
5. PR本文の手動確認手順を相手が再現できる。
6. 未解決のレビューコメントがない。

推奨するマージ順序は次のとおりとする。

| 予定日 | mainへマージする内容 | 理由 |
|---|---|---|
| 7月14日夜 | 両名で合意したモデルとServiceの公開契約、JUnit実行基盤 | 以降の並行実装でAPIの食い違いを防ぐため |
| 7月15日夜 | ryotaのBooks CRUD、kumpeiのMembers CRUD | 互いに独立した基本機能を早期にmainへ固定するため |
| 7月16日夜 | kumpeiの貸出・返却・借用者照会 | BookとMemberの両方がmainに入った後で統合するため |
| 7月17日夜 | ryotaの永続化と、会員・貸出データの保存連携 | 全モデルの保存・再読込を一括確認してから入れるため |
| 7月18日夜 | 検索、期限・延滞表示、異常系テスト、レビュー修正 | 必須機能を壊さないことを回帰テストで確認してから入れるため |
| 7月19日 | レポート、README、提出用スクリプト、最終修正 | この時点を提出候補版とし、新しい機能追加を止めるため |
| 7月20日 | 重大な不具合の修正だけ | 1件ずつ小さなPRにし、両名確認後にマージするため |

同日に複数PRをマージする場合は、依存される側を先にマージする。マージ後、もう一方の作業ブランチは最新の`main`を取り込み、JUnitを再実行してから次のPRをマージする。コミットの著者とPR単位を残すため、原則としてSquash mergeは使用しない。

## 11. 評価を上げるための追加提案

1. GUIの見栄えより先に、操作失敗時にもデータが壊れない業務ルールを完成させる。
2. テスト数だけでなく、在庫0、削除制約、再起動復元など採点者が試しそうな境界値を示す。
3. レポートに画面キャプチャ、クラス構成図、主要ユースケース、テスト結果一覧を載せる。
4. GitHub Actionsで本体コンパイルとJUnitを自動実行し、共同開発と品質管理の証拠にする。
5. 提出前に、JDKしか入っていない環境で本体が動くことを確認する。
